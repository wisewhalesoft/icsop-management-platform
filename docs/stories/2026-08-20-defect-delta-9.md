## 二、逐項驗收意圖（尚非 AC 條文，供 spec-writer 參考；含可機器驗證之觀測點）

### #1 全域浮水印顏色加深
「修好」的判斷：所有浮水印呈現載體（前端 3 處疊加樣式常數＋後端 1 處 PDF 燒錄樣式常數）之顏色值／透明度值，較現行 `#64748b`／`rgb(0.4,0.45,0.5)`／`opacity:0.12` 更深/更不透明，且**四處數值彼此一致**（不得只改其中一兩處）。
- 可機器驗證觀測點：對疊加樣式（前端 CSS-in-JS）與燒錄樣式（`pdf-burner.ts` 之 `rgb()`/`opacity` 常數）做快照/數值斷言；WCAG 對比度計算（若定出目標值，可驗證新色值相對背景之對比度是否落在目標區間）。

### #2 移除檢視頁面套件下載/列印按鈕
「修好」的判斷：使用者在檢視器中，無法再透過瀏覽器/PDF 套件自帶工具列取得未經燒錄的原始 PDF 位元組；本系統自身的「下載」「列印」按鈕（`documentDownloadUrl`/`documentPrintUrl`，皆已燒錄）不受影響、維持可用。
- 可機器驗證觀測點：E2E 層面較難以直接斷言瀏覽器原生 UI 是否存在（因其非本系統 DOM 的一部分，屬瀏覽器 Chrome 層渲染），故此項之機器可驗證性高度依賴**最終採用之技術路線**（見 `OQ-D9-04`）；若改採自繪渲染（如 canvas），則「頁面 DOM 中不存在瀏覽器原生 PDF viewer 之 `<embed>`/`<object>`/裸 `<iframe src=pdf>` 結構」即為可斷言之觀測點。此點請 spec-writer 待架構裁定後再精確化 AC。

### #3 浮水印公司名稱縮寫
「修好」的判斷：浮水印線性快照（`buildWatermarkSnapshot`）之 `companyFullName` 欄位改為短稱；且**波及範圍已被明確界定**（是否連帶影響帳號管理公司下拉、`GET /companies`、F024 調閱稽核公司欄，須先由人類裁決）。
- 可機器驗證觀測點：`watermark.spec.ts` 既有之固定測試向量（含公司名稱片段）需同步更新；若採「浮水印專用簡稱」路線，另需要一個新的 `AS→和潤企業` 對照斷言，且需斷言帳號管理／`GET /companies` 之既有測試**未被連帶改變**（回歸鎖定）。

### #4 檢視頁放大解析度模糊
「修好」的判斷：放大至既有縮放上限時，PDF 文字邊緣清晰度不因純 CSS 點陣縮放而劣化。
- 可機器驗證觀測點：目前 `zoom-label`／`transform: scale()` 屬單元可測之數值邏輯，但「模糊與否」屬視覺呈現、非純邏輯斷言可覆蓋——若沿用現行架構整合測試僅能斷言縮放倍率數值正確，無法斷言清晰度；若改採重新渲染架構，可斷言「zoom 變更時觸發重新渲染」而非「僅套 CSS transform」。

### #5 後台全面燒錄浮水印
「修好」的判斷：**待 `OQ-D9-08` 裁決後才能定義**——因為「修好」的標準完全取決於推翻範圍（維持現狀 / 全面推翻 / 折衷方案 A / 折衷方案 B，見 OQ 選項）。在裁決之前，此項**無法**寫出驗收意圖而不至於與現行已定案基準線衝突。
- 可機器驗證觀測點（僅列出裁決後皆會用到的通用觀測手法，不預設答案）：對應之下載端點是否呼叫 `PdfBurner.burnPdf`（現行 `field-matrix-test-design.md` 之 `TS-FM-001`/`TS-FM-002` 正是以「未呼叫任何燒錄函式」作斷言，若裁決推翻，這兩個測試需被**取代**而非刪除）；下載回應之 PDF 內容層是否含浮水印文字（位元組層驗證，屬 integration）。

### #6 前台字體放大
「修好」的判斷：前台頁面正文/輔助說明字級較現行明確放大，且範圍（僅前台或全站）與幅度已有具體數值依據，不再是「偏小」這種主觀描述。
- 可機器驗證觀測點：Tailwind 字級 class 或 CSS `font-size` 數值之靜態斷言（例如某元件之 class 由 `text-sm` 改為 `text-base`）；既有 pixel-level fidelity/E2E 快照測試若存在，需明確標註本次調整為預期變更（非回歸）。

### #7 使用表單管理頁改版
- (a) 整頁化：「修好」的判斷取決於 `OQ-D9-15` 裁決之範圍（純版面搬遷 vs 連同上傳流程本身改為分步）。純版面搬遷之觀測點＝新增/編輯之操作路徑改為導頁（route 變更）而非彈窗（`role="dialog"` 元素消失，改為獨立頁面）。
- (b) 编号唯一：若最終判定為「既有機制需在新頁面延續」，觀測點＝新頁面提交重複編號時，仍收到 `USAGE_FORM_NUMBER_DUPLICATE`（409）並於畫面呈現既有錯誤文案（`editNumberErrorMessage`，`UsageFormManagementPage.tsx:69-80`）。若判定為「現行機制有實際缺陷」，需先取得使用者提供之重現步驟方可定義驗收意圖。
- (c) 制定部門（多選）：「修好」的判斷取決於 `OQ-D9-17`／`OQ-D9-18` 裁決之資料模型與用途。觀測點（通用）＝新增/編輯畫面可勾選多個部門並持久化；若該欄位僅為顯示用 metadata，機器驗證僅需 CRUD 回歸；若涉及可見性/權限過濾語意，則需比照 F041/F033 之既有子樹展開純函式做回歸測試。

### #8 OJT 上傳破例

### 關於 #1（浮水印顏色加深）

**OQ-D9-01** — 「加深」的具體目標值為何？ **[CLARIFY]**｜相關：F020
現行前端疊加＝`#64748b` + `opacity:0.12`；後端燒錄＝`rgb(0.4,0.45,0.5)` + `opacity:0.12`。
- **選項 A**：僅提高透明度（如 `opacity:0.12→0.20`），色相不變。代價：改動最小，但若使用者期待的是「顏色本身更深（如更接近黑）」而非「更不透明」，會不符期待。
- **選項 B**：僅改色值為更深之灰階（如 `#334155` slate-700），透明度不變。代價：在淺色背景下可能仍不夠醒目；若背景为深色頁面（無此情境）則會過暗。
- **選項 C**：兩者皆調（色更深＋透明度更高），並附帶 WCAG 對比度目標（如「與白底對比度 ≥ 3:1」）作為可驗收之數值依據。
- **建議**：C——「加深」一詞本身同時暗示顏色與能見度，只調其一容易被判定「還是不夠深」；且唯有附帶量化對比度目標，才能寫出可機器驗證的 AC。

**OQ-D9-02** — 「全域」涵蓋哪些浮水印載體？ **[BLOCKING]**｜相關：F020, F037, F038
現況共 4 處疊加樣式常數（`PublicViewerPage.tsx`／`ChangeHistoryPage.tsx`／`LifecycleTreePreviewPage.tsx`）+ 1 處燒錄樣式常數（`pdf-burner.ts`，供文件本體/附件/附錄/使用表單下載）。
- **選項 A**：僅前台檢視器（`PublicViewerPage.tsx`）與實際燒錄（`pdf-burner.ts`）——因為這兩者才是使用者「看得到最終產出」的路徑。代價：變更歷程／循環樹狀圖預覽頁的疊加顏色與其餘 3 處不一致，日後易被回報為「顏色深淺不一」。
- **選項 B**：5 處全動，維持全站一致。代價：改動面較大，變更歷程／循環樹狀圖預覽頁需同步調整並回歸既有 pixel/fidelity 測試。
- **建議**：B——「全域」一詞（使用者原文）本身已暗示不限單一頁面，且既有架構刻意讓 4 處疊加與 1 處燒錄共用同一組色值語意（雖為各自獨立常數），分開調整會製造新的不一致。

### 關於 #2／#4（套件按鈕移除／縮放模糊，同源問題）

**OQ-D9-03** — 是否認定「`/public/documents/:id/pdf` 回傳未燒錄原始位元組供 iframe 顯示、瀏覽器原生工具列可據此直接下載/列印無浮水印檔案」為安全缺陷，需優先處理？ **[BLOCKING]**｜相關：F020, nfr#security

- **建議**：A——使用者原文本身已標註「(無浮水印漏洞)」，顯示使用者已將其定性為安全問題，非單純美觀需求。

**OQ-D9-04** — 移除套件按鈕的技術路線？ **[BLOCKING]**｜相關：F020，需 system-architect 定案

- **建議**：A——因為 #2 與 #4 為同一根因（iframe 交由瀏覽器渲染），且 B/C 皆無法真正解決任一項，A 是唯一能同時處理兩項訴求的路線；但需使用者知悉並接受「引入新前端相依」之代價後，再交 system-architect 定案实作細節。

**OQ-D9-05** — 若選 A（換渲染引擎），#4 之縮放模糊是否併入同一批次一次解決？若不選 A，#4 是否仍需獨立處理？ **[CLARIFY]**｜相關：F020
- **選項 A**：併入同批（隨 #2 一起做，工程上最有效率，避免對檢視器架構動兩次刀）。
- **選項 B**：分批——先做 #2（安全），#4 留待日後（可用性，非安全）。代價：若 #2 最終仍維持 iframe 架構（選 B/C），#4 將**沒有**在不動架構前提下的根治解法，僅能透過提高 iframe 內部渲染解析度等局部緩解手段。
- **建議**：A（承接 `OQ-D9-04` 建議之選項 A 前提下）。

**OQ-D9-08** — 是否推翻 `OQ-FM-01`／`OQ-D18-01`（後台維持 RAW 之定案）？推翻範圍到哪？ **[BLOCKING]**｜相關：F020, F026, F039, F018

### 關於 #7（使用表單管理頁改版）

**OQ-D9-15** — 整頁化的範圍：僅版面搬遷，還是連同新增流程本身改為分步？ **[BLOCKING]**｜相關：F018
現行「新增」為單一 modal，一次 multipart 送出「檔案＋名稱＋選填編號」；ICSOP 文件建立頁（對照樣式）之 STEP 式設計則是「先建立文件記錄取得 UUID，後續步驟才依序上傳附件」（`DocumentCreatePage.tsx:359`：「STEP4 後續步驟：文件建立後方有 UUID，依序上傳附件…」）。
- **選項 A（純版面搬遷）**：僅將 modal 內容原樣搬進整頁排版（分區塊呈現，但仍是「選檔+命名+編號一次送出」之單一動作），不改變後端建立流程與 API 契約。代價：與 ICSOP 文件建立頁的「先建立、後上傳」精神不完全一致，僅視覺樣式趨同。
- **選項 B（比照 STEP 式流程）**：真正比照——先建立表單池記錄（不含檔案）取得 ID，再上傳檔案。代價：需重新設計 `usage-forms` 後端建立流程（現行 `uploadUsageForms` 為一次性 multipart 建立，`usage-forms.service.ts` 無「先建空殼記錄」之路徑），工程量遠高於 A，且需要處理「建立後未上傳檔案」的中間態如何呈現於清單。
- **建議**：A——使用者原文「改為ICSOP文件新增/編輯頁**的方式**處理」較可能指涉版面/操作體驗（整頁 vs 彈窗），而非要求表單池本身改變其「檔案是必要組成」的資料模型本質（使用表單池不像 ICSOP 文件有 20 個欄位需分步填寫，其核心就是「一個檔案＋少量 metadata」，分步的必要性較低）；但此為 analyst 之推測，**建議仍需使用者一句話確認**。

**OQ-D9-16** — 「編號檢查唯一」係要求新增此機制，還是提醒既有機制須沿用到新頁面，或反映此機制現況失效？ **[CLARIFY]**｜相關：F018
唯一性檢查**已存在**：應用層 409 `USAGE_FORM_NUMBER_DUPLICATE`（`usage-forms.service.ts:201-217` 上傳建立時、`:231-256` 編輯編號時）＋ DB filtered unique index（`migrations/1723939200000-usage-form-number.ts`）＋ collation 修正（`migrations/1724025600000-usage-form-number-collation.ts`，此為 2026-08-16 delta 中揪出並修復之真實生產缺陷）。
- **選項 A**：使用者當時未察覺此機制已存在，本項訴求視為「改版時不可遺漏此既有機制」之提醒，本身不構成新工作項（改版後之新增/編輯頁沿用既有 409 錯誤處理與訊息即可）。
- **選項 B**：使用者近期實際操作時遇到重複編號未被擋下（真實缺陷回報），需要具體重現步驟（哪個環境、哪個角色、輸入了什麼編號、是否恰好命中 collation 問題之邊界情況）才能判定是否為 `OQ-D18-30`／`31`／`32` 同型之「三道機器閘門全綠、卻在容器內對真庫實跑才揭露」缺陷。
- **建議**：A，作為預設假設；但**強烈建議** lead 向使用者確認一句「是否曾實際遇到重複編號未被擋下」，因為若答案是 B，這將是與 `OQ-D18-30` 同型態、需要立即比照處理的真實生產缺陷，優先序應該完全不同。

**OQ-D9-17** — 「制定部門（多選）」的資料模型：比照 F014 制定組織三級，或比照 `DOC_USING_DEPT`？ **[BLOCKING]**｜相關：F018, F014, data-model
`USAGE_FORM_POOL` 現行**無**此欄位，需新增資料結構。
- **選項 A**：比照 F014 制定組織三級（`draftingCompanyId`/`draftingDeptId`/`draftingSectionId`）——單一路徑、由上而下相依選取。**但使用者原文明確要求「多選」**，與此模式（單選三級）字面上不符，除非「多選」指的是可複選多組三級路徑（即一份表單可標記多個「制定單位」，每個仍是完整三級）。

- **建議**：B——使用者原文明確用詞「多選」，且該詞在既有規格語境中（F026「文件使用部門（可多筆，可指定任意層級）」）已有精確對應之既有模式，採用一致的既有模式可降低認知負擔與實作風險。

**OQ-D9-18** — 「制定部門」欄位的用途：僅供顯示/篩選之 metadata，還是要用於前台可見性或 RBAC 過濾？ **[BLOCKING]**｜相關：F018, F041, F033, F026
若答案為後者，將牽動 F041（一般使用者業務子分類可見性過濾）／F033（RAG 檢索權限過濾）／F026（角色欄位矩陣）等既有子系統之判定邏輯是否需要納入使用表單之「制定部門」作為新的過濾維度；若答案為前者，則僅是單純 CRUD＋清單顯示/篩選欄位，複雜度低得多。
